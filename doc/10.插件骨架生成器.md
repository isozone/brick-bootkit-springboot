# 插件骨架生成器

本工具根据 `slicer` 分析出的候选切片，**自动生成可编译的插件模块骨架**。

解决的是从"知道切哪块"到"得到能跑的插件"之间的最后一公里。

---

## 前置条件

1. 项目已经跑过 [preflight 体检](./8.旧项目渐进式接入指南.md) 且无阻断项
2. 已经用 [切片分析器](./9.业务切片分析指南.md) 选定了要切的包

---

## 运行

```bash
# 基本用法（输出到 <包名末段>-plugin/）
./tools/scaffold/scaffold.sh /path/to/project com.oldcorp.report

# 指定输出目录
./tools/scaffold/scaffold.sh /path/to/project com.oldcorp.report /path/to/output

# 覆盖已存在的输出目录
./tools/scaffold/scaffold.sh /path/to/project com.oldcorp.report /path/to/output --force
```

参数：

| 参数 | 说明 |
| --- | --- |
| `<项目路径>` | 原始项目根目录 |
| `<包名>` | slicer 候选列表中的包名 |
| `[输出目录]` | 缺省为 `<包名末段>-plugin/` |
| `--force` | 输出目录已存在时覆盖 |

## 生成内容

以 `com.oldcorp.report` 为例，生成后的目录结构：

```
report-plugin/
├── pom.xml
└── src/
    └── main/
        ├── java/
        │   └── com/
        │       └── oldcorp/
        │           └── report/
        │               ├── api/
        │               │   └── ReportService.java      # 契约接口
        │               └── plugin/
        │                   ├── ReportPluginBootstrap.java  # 插件启动类
        │                   ├── ReportPluginInfo.java       # 插件元数据
        │                   └── ReportServiceImpl.java      # 业务实现 stub
        └── resources/
            └── META-INF/
                └── spring.factories
```

### 各文件职责

| 文件 | 职责 |
| --- | --- |
| `pom.xml` | 插件打包配置，含 brick-bootkit 依赖和 maven-packager |
| `*PluginBootstrap.java` | 继承 `SpringPluginBootstrap`，插件独立 Spring 容器入口 |
| `*PluginInfo.java` | 实现 `PluginInfo`，提供 id、版本、描述等元数据 |
| `api/*.java` | **契约接口**：切片后必须暴露给主程序的公共契约 |
| `plugin/*ServiceImpl.java` | 业务实现 stub，含 TODO 标记待迁移 |
| `spring.factories` | Spring Boot 自动装配元数据 |

## 从骨架到可运行插件

生成器已经帮你搭好了框架，但还有几步需要手动完成：

### 1. 检查 pom.xml

- **groupId/artifactId**：生成器从原始 pom 提取，可能需要调整
- **java.version**：生成器从原始 pom 提取，但插件至少需要 JDK 17（brick-bootkit 基线）
- **依赖**：生成器根据 slicer 的外部库分析推断了一些依赖，需确认是否完整

### 2. 迁移契约接口到主程序

把 `api/` 目录下的接口复制到主程序（或独立的 api 模块），让主程序编译通过。

主程序 pom 中声明 api 模块依赖：

```xml
<dependency>
    <groupId>com.oldcorp</groupId>
    <artifactId>report-plugin-api</artifactId>
    <version>1.0.0-SNAPSHOT</version>
</dependency>
```

插件 pom 中把该依赖改为 `<scope>provided</scope>`（由主程序提供）。

### 3. 补全 PluginInfo

```java
public class ReportPluginInfo implements PluginInfo {
    @Override
    public String id() { return "report-plugin"; }

    @Override
    public String version() { return "1.0.0"; }

    @Override
    public String provider() { return "com.oldcorp"; }

    @Override
    public String description() { return "报表插件"; }
}
```

### 4. 迁移业务逻辑

`plugin/*ServiceImpl.java` 中的方法体都是 `// TODO: migrate business logic from original project`，
把原始项目中的业务逻辑搬过来，并补全依赖注入。

### 5. 打包验证

```bash
cd report-plugin/
mvn clean package
```

确认 `target/` 下产出了插件包（通常是 `*-plugin.jar`）。

## 精度边界

生成器基于源码文本解析，存在以下已知限制：

| 限制 | 影响 |
| --- | --- |
| 只提取 `public` 方法（接口方法默认 public 也会被提取） | private/protected 方法不会进入契约接口 |
| 跳过 getter/setter/toString/equals/hashCode | 这些不会出现在契约接口中 |
| 方法签名基于文本匹配 | 泛型边界、异常声明、注解可能丢失 |
| 依赖推断基于 import 分析 | 可能遗漏运行时依赖或间接依赖 |
| 不处理配置类迁移 | `@Configuration` 类需手动评估是否移到插件 |

结论：**生成器产出的是骨架，不是可直接生产的代码。** 契约接口的方法签名、依赖声明、业务逻辑都需要人工审校。

## 与 slicer 的配合

典型的切片工作流：

```bash
# 1. 分析候选
./tools/slicer/slice.sh /path/to/project

# 2. 选定一个候选包（比如评分最高的 report）
# 3. 生成骨架
./tools/scaffold/scaffold.sh /path/to/project com.oldcorp.report

# 4. 按上文"从骨架到可运行插件"的步骤补全
# 5. 用 L0/L1/L2 逐级验证
```

## 与现有模板的区别

| | 最小模板 `plugin-minimal` | 骨架生成器 |
| --- | --- | --- |
| 目标 | 从零开始写插件 | 从存量代码迁移出插件 |
| 输入 | 无 | slicer 分析结果 + 原始源码 |
| 产出 | 空白模板 | 含契约接口和业务 stub 的半成品 |
| 适用场景 | 全新插件开发 | 存量项目拆分 |
