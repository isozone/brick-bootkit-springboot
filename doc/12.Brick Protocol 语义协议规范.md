# Brick Protocol 语义协议规范

> 定位于「设备/服务接入的语义世界语」：brick 仍是 Spring Boot 插件框架，本项目只定义**语义协议规范**，
> 硬件设备、跨进程插件只要适配了这套规范，服务层就能开发对应的业务完成调用，无需关心底层传输。
> 核心原则：**语义协议与传输协议彻底分离**。

## 一、两层协议

协议分成两层，各管各的、永不越界：

| 层 | 内容 | 谁定义 | 例子 |
|---|---|---|---|
| **传输协议** | 设备怎么连、字节怎么传、报文怎么编码 | 设备厂商（非本项目） | Modbus、MQTT、BLE、串口 |
| **语义协议** | 设备「能做什么」的统一模型（点/命令/事件/消息形状） | **本项目（brick）** | 本节全部内容 |

翻译发生在 **adapter**：

```
[Modbus 寄存器 40001]  --adapter-->  [capability: temp, +23.5°C]
[BLE 特征通知 0x2A6F]  --adapter-->  [capability: temp, +23.5°C]
```

业务层只看到 `temp=23.5`，不知道（也不准关心）底下是 Modbus 还是 BLE。

### 宪法（评审底线，任何时候不得破坏）

1. **信封内永无传输细节**——`modbus 地址 / MQTT 主题 / 特征 UUID / 波特率` 只允许出现在 adapter 内部或 adapter 配置里，永远不许出现在语义协议消息中。
2. **`protocol` 模块零外部运行时依赖、不依赖 `core`**——协议是"世界语"，其他框架/语言的插件都要能依赖它；一旦依赖 core 就变成 Java Spring 专属。
3. **具体能力不进协议规范**——协议不列出"温度/湿度/开关"，只保证"任何能力都能被表达"；具体能力是运行时由 adapter 声明出来的数据。
4. **信封四种类型不扩枚举**——新语义靠组合，不新增 type。
5. **现有 EventBus 能力不复造**——协议只给现有消息定义标准化 wire 形状，不另起炉灶。

### 两类设备（两层分离的自然推论）

- **普通设备**（绝大多数）：只懂自己的传输协议 → 需要写一个 adapter 翻译。
- **brick-native 设备**（未来自家硬件或 SDK 设备）：直接讲语义协议，零 adapter，天生一等公民。

### in-process 也是一种传输协议

brick 插件之间的 JVM 内调用，本质就是一种传输协议（对象在内存传递）。协议化 = 给一堆方言立统一世界语：

```
in-process 插件调用  ----\
MQTT 设备上报        ----+---- 语义协议（唯一世界语）
Modbus adapter      ----/
gRPC 跨进程插件      ----/
```

"跨进程插件""硬件设备""本地插件"不再三个东西，而是同一个语义协议放在不同传输上。

## 二、模块划分

```
spring-boot3-brick-bootkit-protocol   ← 新增。协议规范本体，零第三方运行时依赖
spring-boot3-brick-bootkit-core       ← 改动。依赖 protocol，集成进 EventBus / PluginManager / DeviceRegistry
spring-boot3-brick-bootkit              ← 改动。聚合 module + 示例 adapter
```

依赖方向：`protocol → common`；`core → protocol`。**反向禁止。**

## 三、消息信封（语义协议的心脏）

### 3.1 信封定义

```json
{
  "version": "1.0",
  "type": "event",              // request | reply | event | command
  "messageId": "a1b2c3...",     // 全局唯一
  "correlationId": "",          // 仅 reply 回填，关联 request/command
  "deviceId": "sensor-01",
  "capabilityId": "temp",
  "timestamp": "2026-09-10T16:00:00Z",
  "qos": 1,                     // 0 fire-forget / 1 at-least-once
  "from": "adapter-modbus",
  "payload": { "value": 23.5, "unit": "°C" }
}
```

### 3.2 字段语义

| 字段 | 含义 | 说明 |
|---|---|---|
| `version` | 语义协议自身版本 | 用于兼容性判定 |
| `type` | 消息类型 | 四种：request/reply/event/command |
| `messageId` | 全局唯一消息ID | reply 靠它关联（correlationId 回填） |
| `correlationId` | 关联ID | 仅 reply 使用，回填被应答消息的 messageId |
| `deviceId` | 逻辑设备标识 | 寻址的第一层 |
| `capabilityId` | 逻辑能力标识 | 寻址的第二层 |
| `timestamp` | 消息产生时间 | UTC |
| `qos` | 可靠性等级 | 0=fire-forget，1=at-least-once |
| `from` | 发件人 | 跨进程路由回程用 |
| `payload` | 业务载荷 | 与信封分离，协议演进不污染业务数据 |

设计依据：

- **信封/载荷分离**：字段集是协议，`payload` 是业务，互不污染。
- **逻辑寻址**：地址只能是 `deviceId+capabilityId`，任何传输痕迹禁入。
- **类型即语义**：方向由 type 隐含——request/command 下行，reply/event 上行，不需要额外 direction 字段。
- **无 direction**：减少字段，避免消息存在"两个方向都对"的歧义。
- **序列化与语义分离**：v1 用 JSON（零依赖、可调试），但协议是 schema 不是编码——同一信封可换 CBOR/protobuf 不换语义，为 gRPC/WASM 铺路。

### 3.3 四种消息流转

```
command:  业务层 → 设备      (告诉设备"执行/写值"，期待 reply)
reply:    设备 → 业务层      (command/request 的应答，correlationId 关联)
request:  业务层 → 设备      (同步读值，期待 reply)
event:    设备 → 任意订阅者  (主动上报，单向下行无回包 / 或订阅)
```

典型流转：**业务层发 `command` 关继电器 → adapter 翻译成 Modbus 写线圈 → 设备回执 → adapter 翻译回 `reply` 带回 messageId**。业务层全程只见过信封，没见过 Modbus。

## 四、能力模型（运行时数据，不是协议硬编码）

### 4.1 抽象结构

```
device "sensor-01"
├── point  temp     (可读)     // 状态/值
├── point  relay    (可读可写) // 状态/值
├── command reset   (动作)     // 一次性动作，非状态
└── event   overheat (上报)     // 主动通知
```

- `Capability` 抽象：`PointCapability`（可读/可写状态值）、`CommandCapability`（一次性动作）、`EventCapability`（主动上报）三个子抽象。
- 具体能力类型（temperature、switch…）**不进协议规范**，由 adapter 在运行时声明，登记 `DeviceRegistry`。

### 4.2 生命周期语义

协议只定义三个标准事件信封（用 `capabilityId="lifecycle"` 的 event 表达）：

- `device.online`
- `device.offline`
- `device.heartbeat`

重连/心跳的真实含义由传输层（adapter）解释，协议层只管"状态变了这件事被表达"。

## 五、适配层（adapter SPI）——设备如何适配规范

设计为**声明式映射打底 + 命令式 adapter 兜底**。

### 5.1 声明式映射表（99% 场景够用）

adapter 插件的 `resources/brick-adapter.json`：

```json
{
  "deviceType": "modbus-thermostat",
  "transport": "modbus",
  "mappings": [
    { "capability": "temp",   "type": "point",   "access": "read",        "register": 40001, "scale": 0.1 },
    { "capability": "relay",  "type": "point",   "access": "read-write",  "register": 48001 },
    { "capability": "reset",  "type": "command",                          "register": 40011, "writeValue": 1 }
  ]
}
```

- 声明式是底座：非 Java 人员也能接设备；adapter 是"能力翻译字典"。
- 权威字段（`register` 等）出自 adapter 配置，而非信封——再次守住"传输痕迹不过界"。

### 5.2 命令式 SPI（传输稀奇古怪时兜底）

```java
public interface DeviceAdapter {
    String getDeviceType();
    void connect();                              // 建立传输链路
    Object toDevice(CommandEnvelope cmd);        // 语义 → 传输报文
    void onFromDevice(BrickEnvelope event, TransportContext ctx); // 传输 → 语义
    void disconnect();
}
```

声明式覆盖不了的协议（私有二进制、双向长连接）用这个写。

## 六、与现有运行时的咬合（改动最小化）

| 现有能力 | 协议层用法 |
|---|---|
| **EventBus 的 pub/sub + request/reply** | 信封就是 EventBus 消息的**标准化 payload**。协议不另起炉灶，只给规范化 wire 形状 |
| **PluginManager 生命周期** | adapter 插件、业务插件沿用现有启动/停止/卸载；设备 online/offline 事件挂钩插件生命周期 |
| **类加载隔离** | 一个 adapter 一个插件包，天然隔离各厂商依赖 |
| **Web 控制台** | 复用现有插件管理页，增加"设备接入"视口 |

**关键新增**：`DeviceRegistry`（core 中）——设备接入/离线的注册表。业务插件查 `registry.lookup("sensor-01")` 拿能力，然后直接发信封。这是业务层唯一的入口依赖，屏蔽 adapter 存在。

```
业务层  ── 只认语义协议(能力树)，开发订单/报表/联动逻辑
  ↑
协议层  ── brick 定义：能力模型 + 消息格式 + 生命周期（本项目只做这层）
  ↑
适配层  ── Modbus/MQTT/BLE 各一个 adapter，把厂商报文翻译成能力树
设备    ── 只要有人给它写 adapter，它就能"上岗"
```

## 八、验收标准（协议正确性的判断依据）

1. 业务层代码中 grep 不到任何 `modbus|register|uart|topic` 等传输关键字。
2. `protocol` 模块 `mvn dependency:tree` 运行时依赖为空（或仅 common）。
3. 同一个业务插件，切换 Modbus adapter → BLE adapter，业务代码零改动。
4. 信封只有四种 type，`BrickMessageType` 枚举不随新增设备类型而增长。
5. 移除 EventBus，协议仍可独立测试（协议不依赖运行时）。
