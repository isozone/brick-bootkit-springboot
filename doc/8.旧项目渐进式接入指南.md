# 旧项目渐进式接入指南

本指南面向**存量 Spring Boot 项目**。新项目请直接用 [2.SpringBoot项目快速接入指南](./2.SpringBoot项目快速接入指南.md)。

## 为什么要分两级来做

存量系统接入插件框架，真正的阻力不是"加一个依赖"这五分钟，而是两个没人回答的问题：

1. **我这项目到底能不能接？** —— 有没有硬阻断项（JDK、Spring Boot 版本、部署形态、已有 Agent）。
2. **接进去会不会失控？** —— 旧系统经不起"接完启动不起来"这种试错。

框架为此提供两件事：

- **preflight 体检器**：在**不改一行代码、不加任何依赖**的前提下，离线判断能不能接。
- **渐进式接入级别**：把接入拆成 L0 / L1 / L2 三级，逐级放开，任何一级都可以停在原地不动。

> 现有的 `doctor`（`GET /plugins-web/api/doctor`）是**运行时**自检，必须先接入才能用。
> preflight 解决的是"接入之前"的空档，两者分工不同，建议先后各跑一次。

## 第一步：离线体检（preflight）

### 运行

```bash
# 在本仓库下执行
./tools/preflight/preflight.sh /path/to/your/project

# 不想 clone 仓库，也可以直接跑单文件（需要 JDK 17+）
java tools/preflight/Preflight.java /path/to/your/project

# CI 场景用 JSON 输出
./tools/preflight/preflight.sh /path/to/your/project --json
```

体检器是**零第三方依赖的单文件 Java 程序**，通过 JDK 单文件源码模式运行：
不会编译你的项目，不会下载依赖，也不会修改目标项目的任何文件。

### 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 无阻断项，可以继续接入 |
| `1` | 存在阻断项，需要先解决 |
| `2` | 参数或路径错误（例如 JDK 版本不足、目录不存在） |

可直接在 CI 里用退出码卡门禁。

### 检查项

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `PF001` | 阻断 | 未找到 `pom.xml` 或 `build.gradle` |
| `PF002` | 阻断/通过 | Spring Boot 版本是否达到 3.x |
| `PF003` | 阻断/警告 | 能否识别 Spring Boot 依赖管理 |
| `PF004` | 阻断/通过 | JDK 版本是否达到 17 |
| `PF005` | 警告 | 无法从 pom 确定 Java 版本 |
| `PF010` | 警告/通过 | `packaging=war`（外置容器，类加载层次不受控） |
| `PF011` | 警告 | Gradle 项目（不在支持矩阵内） |
| `PF012` | 警告 | 根工程为 `pom` 聚合工程，结论会被稀释 |
| `PF020` | 警告/通过 | 能否扫描到唯一启动类 |
| `PF021` | 警告 | 存在多个启动类，`mainPackage` 推断有歧义 |
| `PF022` | 警告 | 启动类配置了多个 `scanBasePackages` |
| `PF030` | 警告 | 纯 WebFlux 宿主（控制台基于 Servlet 栈） |
| `PF031` | 警告 | 存在 Spring Security，需放行控制台路径 |
| `PF032` | 警告 | fastjson 1.x（与类隔离组合问题较多） |
| `PF033` | 警告 | Java Agent 相关依赖（skywalking / arthas / jacoco） |
| `PF034` | 警告 | 自带类加载体系的组件（dubbo / shardingsphere） |
| `PF040` | 警告 | 多模块项目 |

### 输出解读

体检报告会给出三项可直接落地的结论：

- **建议的 `plugin.mainPackage`** —— 取自启动类所在包。
- **推荐的接入级别** —— `NONE` / `L0` / `L1`，有阻断项时为 `NONE`。
- **下一步动作** —— 按级别给出不同指引。

> 关于 `mainPackage`：框架的自动推断依赖 `AutoConfigurationPackages` 的第一个包。
> 旧项目多 `scanBasePackages`、多模块、非标准启动类时，推断出的包**可能过宽**——
> 而过宽会导致插件里的类被主加载器抢走，表现为极难排查的 `ClassCastException`。
> 因此体检器只要发现风险，就会建议你**显式配置**。

## 第二步：三级接入阶梯

三个级别由两个开关组合而成，两个开关默认都是 `true`，即历史默认行为（全量模式）。

| 级别 | `autoLoadPlugins` | `autoStartPlugins` | 框架做什么 |
| --- | --- | --- | --- |
| **L0 影子模式** | `false` | 任意 | 完成全部 Bean 装配，**不读取插件目录** |
| **L1 观察模式** | `true` | `false` | 解析插件包并完成校验，**不自动启动** |
| **L2 全量模式** | `true` | `true` | 加载并自动启动（默认行为） |

### L0 影子模式：先证明"装上不影响"

```yaml
plugin:
  enable: true
  mainPackage: com.your.company
  autoLoadPlugins: false
```

这一级的目标是**零业务影响**：依赖引进去了，框架装配完了，但插件机制完全没有介入运行。
适合用来验证：

- 传递依赖是否与现有依赖冲突（启动不报错即通过）
- 主包配置是否正确（框架不会因找不到插件而失败）
- `doctor` 是否可用

启动日志会出现：

```
插件框架处于影子模式（plugin.autoLoadPlugins=false）：已跳过插件目录扫描与加载。
```

此时 `doctor` 会给出 `ADOPTION_LEVEL_SHADOW` 警告——这是**预期行为**，不是故障。

手动安装、启动插件不受此开关限制，你仍然可以在控制台上传插件并手动启动。

### L1 观察模式：验证插件包本身合格

```yaml
plugin:
  enable: true
  mainPackage: com.your.company
  pluginPath:
    - ./plugins
  autoLoadPlugins: true
  autoStartPlugins: false
```

这一级框架会读取插件目录，完成**解析、格式校验、依赖分析、安全准入检查**，
但不会启动任何插件。适合用来验证：

- 插件包是否按框架要求打包（对应故障模板 `plugin-broken-packaging`）
- 插件依赖是否完整
- 安全准入是否被拦截

启动日志会报告解析到的插件数量。确认无误后，再升级到 L2。

### L2 全量模式

```yaml
plugin:
  enable: true
  mainPackage: com.your.company
  pluginPath:
    - ./plugins
```

即默认行为，加载并自动启动插件。

## 第三步：每级的验收清单

**L0 通过标准**

- [ ] 宿主启动无异常
- [ ] 日志出现影子模式提示
- [ ] 接入 web 模块后 `GET /plugins-web/api/doctor` 可访问
- [ ] 现有业务功能无回归

**L1 通过标准**

- [ ] 日志报告的插件数量与预期一致
- [ ] 控制台能看到插件，状态不是"已启动"
- [ ] 插件的依赖与准入检查无 ERROR

**L2 通过标准**

- [ ] 插件状态为已启动
- [ ] 插件接口可正常访问
- [ ] 停止、卸载、重启均正常

## 常见旧项目场景对照

| 场景 | 体检结论 | 处理建议 |
| --- | --- | --- |
| Spring Boot 2.x | 阻断 | 4.x 面向 Spring Boot 3.x。请改用 brick-bootkit 3.x（不在官方回归范围），或先升级框架 |
| JDK 8 / 11 | 阻断 | 基线为 JDK 17，同上 |
| 外置 Tomcat（`war` 包） | 警告 | 类加载层次不受框架控制，建议先改为内嵌容器验证 |
| 多模块聚合工程 | 警告 | 对真正承载启动类的模块单独再跑一次体检 |
| 已接入 Spring Security | 警告 | 放行 `/plugins-web/**`，或实现 `PluginWebAuthorizer` 做鉴权委托 |
| 已有 skywalking / arthas | 警告 | Agent 会改写字节码，务必在预发环境验证插件隔离 |
| 纯 WebFlux | 警告 | 不要引入 web 模块，只用核心能力 |
| Gradle 构建 | 警告 | 官方仅验证 Maven 打包器，需自行验证打包链路 |

## 与 doctor 的分工

| | preflight | doctor |
| --- | --- | --- |
| 时机 | 接入**之前** | 接入**之后** |
| 依赖 | 不需要引入任何依赖 | 需要已接入框架 |
| 形态 | 离线命令行 | 运行时 HTTP 接口 |
| 回答的问题 | 能不能接、从哪级开始 | 接得对不对 |

建议顺序：**preflight → L0 → doctor → L1 → doctor → L2 → doctor**。
