# 业务切片分析指南

本指南回答存量系统接入插件框架时**最难、也最容易拍脑袋**的那个问题：

> 我这一个几百个类的单体，**先切哪一块出去做插件**？

前置条件：项目已经跑过 [preflight 体检](./8.旧项目渐进式接入指南.md) 且无阻断项。
体检解决"能不能接"，本指南解决"接进来之后怎么切"。

---

## 为什么不要靠拍脑袋

常见的三种选法都有明确的失效场景：

| 常见选法 | 失效原因 |
| --- | --- |
| 按功能模块切（订单、用户） | 看起来最自然，但订单和用户往往互相依赖，切走一个另一个编译不过 |
| 挑代码量最多的切 | 代码量大通常意味着它是核心域，被依赖最多，恰恰最不该切 |
| 挑最独立的工具类切 | 独立但无业务价值，切出去省不下任何发版成本 |

真正决定切片代价的是**耦合结构**，不是代码量，也不是业务重要度。
分析器做的事情就是把耦合结构量化出来，让人在这个基础上做判断。

## 运行

```bash
# 在本仓库下执行
./tools/slicer/slice.sh /path/to/your/project

# 不想 clone 仓库，直接跑单文件（需要 JDK 17+）
java tools/slicer/SliceAnalyzer.java /path/to/your/project

# 只要前 3 个候选
./tools/slicer/slice.sh /path/to/your/project --top 3

# 手工指定聚合粒度（默认自动推断）
./tools/slicer/slice.sh /path/to/your/project --depth 4

# 程序化消费
./tools/slicer/slice.sh /path/to/your/project --json
```

与 preflight 一致：零第三方依赖的单文件 Java 程序，**不编译、不下载依赖、不修改目标项目的任何文件**。

参数：

| 参数 | 说明 |
| --- | --- |
| `<项目路径>` | 要分析的项目根目录，缺省为当前目录 |
| `--top N` | 展示前 N 个候选（默认 8） |
| `--depth N` | 按包名前 N 段聚合，默认自动推断 |
| `--json` | JSON 输出 |
| `-h` / `--help` | 帮助 |

> 退出码恒为 `0`。这是一个**建议性**工具，输出的是排序与风险提示，
> 不存在"通过/不通过"的判定，因此不适合直接当 CI 门禁使用；要做门禁请用 preflight。

## 输出怎么读

一份真实的分析结果（合成的单体项目，26 个类）：

```
候选切片（按适宜度排序）

  1. com.oldcorp.report   评分 52
     类 5 个 | 依赖 1 个包 | 被 1 个包依赖 | 外部库 1 组
     需要主程序提供: common
     切出后主程序需改: web
     对外契约类 1 个（切片后需抽象为接口）:
       - ReportService  被 1 个包引用
     风险: 无明显风险

  2. com.oldcorp.infra   评分 49
     ...
     风险:
       ! 含配置类 / 启动类，切片时需迁移自动装配元数据

  3. com.oldcorp.web   评分 37
     ...

  4. com.oldcorp.user   评分 6
     风险:
       ! 存在循环依赖，需先解环
       ! 含 JPA 实体，跨插件边界的持久化上下文与事务需单独设计

  5. com.oldcorp.order   评分 3
     风险:
       ! 存在循环依赖，需先解环

不建议作为切片（共享层 / 基础设施）

  com.oldcorp.common   被 4 个包依赖，类 5 个
      -> 适合下沉为共享库由主程序提供，而不是切进插件

参与循环依赖的包（2 个）

  com.oldcorp.order  <->  com.oldcorp.user
  com.oldcorp.user  <->  com.oldcorp.order
```

### 指标含义

| 指标 | 含义 | 切片含义 |
| --- | --- | --- |
| `fanIn` | 多少个**其他包**依赖它 | 越高越是被复用的共享层，越不该切 |
| `fanOut` | 它依赖了多少个其他包 | 越高说明越不独立，切出去要拖一堆东西 |
| 外部库组数 | 依赖的第三方库分组数 | 越多，插件包越臃肿、越容易和宿主冲突 |
| 对外契约类 | 被其他包引用的类 | 这些就是切片后**必须抽象成接口**暴露给主程序的部分 |
| 循环依赖 | 与其他包双向依赖 | 无法单独切出，必须先解环 |

**需要主程序提供 / 切出后主程序需改**这两行是最直接的行动项：
前者是插件要向宿主索取的能力，后者是切片会波及的调用方。

### 适宜度评分

评分只用于**排序**，不具备绝对含义。计算方式（初始 60 分）：

| 项 | 影响 |
| --- | --- |
| 每个 `fanIn` | `-6` |
| 每个 `fanOut` | `-3.5` |
| 每个外部库组 | `-0.7` |
| 类数量（上限 30） | `+0.5` / 个 |
| 含 JPA 实体 | `-12` |
| 含数据访问层 | `-8` |
| 含配置类 / 启动类 | `-6` |
| 含 HTTP 接口 | `-4` |
| 处于循环依赖 | `-15` |
| 每个被 3 个以上包引用的契约类 | `-10` |

惩罚项的取值来自"这类东西跨插件边界时的实际麻烦程度"：
JPA 实体跨边界会牵扯持久化上下文和事务，所以罚得最重；
HTTP 接口只是路由前缀会变，罚得最轻。

## 从报告到切片边界

**第一步：先看循环依赖段。** 有环的包先排除——不是不能切，是要先解环，
否则切走任何一方另一方都编译不过。解环的常规做法是把双方共用的类型抽到第三个包，改成单向依赖。

**第二步：跳过"不建议作为切片"清单。** fanIn 高的包是共享层，
正确做法是**下沉为共享库由主程序提供**，插件通过主程序暴露的接口访问，而不是把它打进插件。

**第三步：从评分最高的候选开始评估。** 重点看两件事：
它依赖什么（能不能由主程序提供），以及谁依赖它（改动面有多大）。

**第四步：把"对外契约类"抽象成接口。** 这是切片落地时真正的工程量所在。
契约类越多、被越多包引用，接口抽象和调用方改造的成本越高。

**第五步：生成插件骨架。** 用骨架生成器自动产出可编译的插件模块：

```bash
./tools/scaffold/scaffold.sh /path/to/project com.oldcorp.report
```

详见 [10.插件骨架生成器](./10.插件骨架生成器.md)。

**第六步：用 L0/L1/L2 逐级验证。** 切片完成后按
[8.旧项目渐进式接入指南](./8.旧项目渐进式接入指南.md) 的阶梯推进，不要一步到位。

> 最后仍然要结合业务语义判断。分析器只认识代码结构，
> 它不知道某个包下个月要重构，也不知道某块业务有合规要求不能独立部署。

### 粒度不合适时

`--depth` 决定按包名前几段聚合。自动推断取的是"绝大多数类都认同的包前缀 +1"，
如果候选看起来过粗（一个大包什么都有）或过细（每个包只有两三个类），手动调这个参数：

```bash
./tools/slicer/slice.sh /path/to/your/project --depth 5
```

多模块工程会只分析根 pom 中 `<modules>` 声明的模块，
示例工程、脚手架目录不会被算进业务代码。

## 精度边界

分析器采用**源码文本解析**而非字节码分析，换取"无需编译即可运行"的体验。
这是有意的设计取舍——切片决策往往需要在项目能顺利构建**之前**就做出来
（旧项目经常要先把 JDK、框架版本升上来才编得过）。

由此带来的已知限制，请在使用时心里有数：

| 限制 | 影响 |
| --- | --- |
| 只统计跨包引用 | **同包内的相互依赖不进入统计**，聚合粒度越粗，这部分越多 |
| 基于 import 识别依赖 | 使用全限定名内联引用（不写 import）的场景会被漏掉 |
| 不解析语法树 | 注释、字符串里的 `import` 已在行首锚定过滤，但极端写法仍可能误判 |
| 注解为文本匹配 | 只要文件里出现 `@Entity` 等字样即标记，不校验是否真的加在类上 |
| 只扫 `src/main/java` | 测试代码、Kotlin / Groovy 源码、Lombok 生成代码不在范围内 |
| 不区分编译期/运行期依赖 | 依赖强度一视同仁 |

结论：**它给出的是排序和风险提示，不是可以直接照搬的拆分方案。**
把它当成"先看哪几个包"的筛子，而不是"照着切就完事"的图纸。

## 三个工具的分工

| | preflight | **切片分析器** | doctor |
| --- | --- | --- | --- |
| 时机 | 接入**之前** | 接入**之前** | 接入**之后** |
| 回答的问题 | 能不能接 | 切哪一块 | 现在跑得对不对 |
| 是否需要改动项目 | 否 | 否 | 需要先接入 |
| 结论形态 | 阻断 / 警告 | 排序 + 风险提示 | 检查项清单 |
| 适合当 CI 门禁 | 是（看退出码） | 否（建议性） | 否 |

建议顺序：`preflight` 确认可接 → `切片分析器` 选定边界 → L0/L1/L2 逐级接入 → `doctor` 持续自检。
