# 分布式插件模块（spring-boot3-brick-bootkit-distributed）

> 解决「插件越来越多 → 单机资源膨胀」「多机部署 → 每台重复装插件」两大困境。
> 核心思路：**把「插件部署位置」与「服务调用方式」解耦**——插件不再必须在调用方本地加载，
> 而是部署到分布式的「执行节点」，调用方通过 gRPC 透明地远程调用。

## 一、解决的问题

当前框架是「绑定式部署」：一台机器要对外提供某插件的能力，就必须在本地把该插件加载进 JVM
（占用独立 Spring 容器、类加载器、内存）。插件一多，单机资源就爆；想扩多机，每台又得重复装全部插件。

本模块通过 **分布式插件执行模型** 改变这一局面：

- **宿主节点（HOST）**：只跑核心 + 服务路由，**不装插件**，非常轻。
- **执行节点（WORKER）**：每个节点只承载**一部分**插件，按业务/租户/负载切分，绝无重复部署。
- **Redis 服务目录**：执行节点把自己承载的「插件 → 服务接口 → 节点地址」登记进 Redis。
- **gRPC 泛化调用**：宿主调用某插件服务时，先查 Redis 目录找到持有该服务的执行节点，
  再通过 gRPC 把方法调用转发过去，由执行节点在本地插件容器中执行后回传结果。

对调用方完全透明，仿佛本地调用一样。

## 二、架构数据流

```
                宿主节点 (HOST)                      执行节点 (WORKER)
              ┌───────────────────┐               ┌─────────────────────┐
  业务代码     │                   │   gRPC 调用    │                     │
 ┌──────────┐ │  DistributedServiceLocator          │  插件 Spring 容器    │
 │ getService│→│  → 查本地注册中心                    │  (真实插件实例)       │
 └──────────┘ │  → 未命中则查 Redis 目录  ──────────→│  PluginInvocation   │
              │  → 命中返回远程代理       (channel)  │   ServiceImpl       │
              │  RemoteInvocationHandler             │  反射执行目标方法    │
              └───────────────────┘               └─────────────────────┘
                      │  ▲
                      │  │ 注册 / 心跳续期(Redis TTL)
                      ▼  │
              ┌───────────────────┐
              │  Redis 服务目录     │
              │  svc:{接口名}      │
              │   → Hash{pluginId@nodeId: JSON} │
              └───────────────────┘
```

## 三、环境要求

- JDK 17+
- Spring Boot 3.5+
- Maven 3.6+（需联网下载 `protoc` 与 `protoc-gen-grpc-java`，首次构建会下载）
- Redis（执行节点与宿主节点必须**共用同一个 Redis**，作为服务目录）

## 四、依赖引入

在宿主 / 执行节点工程引入：

```xml
<dependency>
    <groupId>com.zqzqq</groupId>
    <artifactId>spring-boot3-brick-bootkit-distributed</artifactId>
    <version>4.0.9</version>
</dependency>
<!-- 必须有 Redis -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

## 五、配置

### 5.1 执行节点（WORKER，承载插件，对外提供 gRPC 调用入口）

```yaml
plugin:
  distributed:
    enabled: true
    role: WORKER        # 关键：执行节点
    port: 9090          # 本节点 gRPC 监听端口，供宿主远程调用
    node-id: worker-1   # 强烈建议显式配置：保证重启后节点身份稳定，避免残留陈旧注册
    registry-prefix: brick-bootkit:distributed:services
    heartbeat-ttl-seconds: 30
    heartbeat-interval-seconds: 10
```

`node-id` 说明：用于在 Redis 目录中唯一标识本节点。建议在多节点时显式配置
（如 `worker-1`/`worker-2`）；不配置时自动回退为「本机 IP + 端口」。
它也会优先复用框架集群的 `clusterNodeRegistry.getNodeId()`（若已启用集群）。

执行节点启动后，会：
1. 启动 gRPC 服务端监听 `9090`；
2. 周期性扫描本地插件服务注册中心，把每个「插件提供的能力」登记到 Redis；
3. 定时续期（通过 Redis TTL 实现节点/服务自动过期下线）；
4. 会话内陈旧节点的注册会在查询时依据字段时间戳自动清理，防止把请求路由到已下线节点。

### 5.2 宿主节点（HOST，消费远端插件能力）

```yaml
plugin:
  distributed:
    enabled: true
    role: HOST          # 关键：宿主节点
    call-timeout-millis: 5000
```

宿主节点不启动 gRPC 服务端，只保留服务目录查询 + 远程代理能力。

### 5.3 单机同时承载 + 消费（可选）

若单节点既想在自己承载的插件上工作、又想消费其他节点的插件，可配 `role: WORKER`
（WORKER 同样具备发现+代理能力）。

## 六、使用方式

### 6.1 定义契约接口

> **接口与 DTO 建议定义为共享类型**（放到主应用或独立 contract 模块），便于宿主在做类型
> 解析时直接加载。执行节点侧已具备**插件类加载器感知**——当接口只存在于插件 jar 时，
> 会从插件已注册服务的类加载器中解析，因此接口/DTO 是否放进共享 classpath 不再是硬性约束；
> 但仍建议对外契约放共享模块，语义最清晰。

```java
public interface UserService {
    String getUserName(Long userId);
    UserInfo getUserInfo(Long userId);
}
```

### 6.2 执行节点侧：在插件中实现并注册服务

插件内实现接口，并用框架的 `@PluginService` 注解注册（框架自动装配会将插件服务注册到
`PluginServiceRegistry`，分布式调度器会把它同步到 Redis 目录）：

```java
@PluginService(interfaceClass = UserService.class, version = "1.0.0", name = "user-service")
public class UserServiceImpl implements UserService {
    @Override
    public String getUserName(Long userId) {
        return "User-" + userId;
    }
}
```

### 6.3 宿主节点侧：远程调用

通过 `DistributedServiceLocator`（推荐）或 `DistributedPluginServiceRegistry` 调用，
与本地调用完全一致：

```java
import com.zqzqq.bootkits.distributed.DistributedServiceLocator;

UserService userService = DistributedServiceLocator.service("user-plugin", UserService.class);
String name = userService.getUserName(1L);   // 透明地执行在远端节点
```

也可以注入 `DistributedPluginServiceRegistry`：

```java
@Autowired
private DistributedPluginServiceRegistry registry;

public void call() {
    UserService svc = registry.getService("user-plugin", UserService.class);
    UserInfo info = svc.getUserInfo(99L);
}
```

### 6.4 判断服务可用性

```java
boolean ok = DistributedServiceLocator.available("user-plugin", UserService.class);
```

> 💡 **想要一步一步真正跑通远端调用？**
> 请阅读《[7.远端调用开发指南](./7.远端调用开发指南.md)》——从环境准备、WORKER/HOST
> 双节点搭建、插件实现与注册、REST 验证到故障排查，全程可复制可执行。

### 6.5 安全配置（TLS + 鉴权 + 多网卡）

生产环境建议开启 **TLS 加密 + token 鉴权**，并显式指定监听 IP。

**WORKER 执行节点（需保证证书/私钥/CA 可用）：**

```yaml
plugin:
  distributed:
    enabled: true
    role: WORKER
    host: 10.0.0.21          # 多网卡时显式指定业务网段 IP（监听 + 注册地址）
    tls-enabled: true
    tls-cert-chain: /etc/brick/certs/server.crt   # PEM 证书链（叶子 + 中间证书）
    tls-private-key: /etc/brick/certs/server.key  # PEM 私钥（PKCS#8）
    auth-token: change-me-shared-secret           # 两端必须一致
```

**HOST 宿主节点：**

```yaml
plugin:
  distributed:
    enabled: true
    role: HOST
    tls-enabled: true
    tls-ca-cert: /etc/brick/certs/server.crt      # 用于校验执行节点证书（信任其 CA / 自签证书）
    auth-token: change-me-shared-secret           # 必须与执行节点一致
```

> ⚠️ TLS 与 token 的启用状态在所有节点必须**一致**（要么全部明文，要么全部启用）。
> token 建议配合 TLS 使用，避免在明文中传输。

> 🔑 **快速开局**：本模块内置一键生成自签证书脚本——
> `spring-boot3-brick-bootkit-distributed/gen-cert.sh`（Linux/macOS/Git Bash）
> 或 `gen-cert.bat`（Windows）。它会产出 `server.key` / `server.crt` / `ca.crt`
> 三件套，并打印两端 yml 配置建议，方便几分钟内跑通 TLS。

## 七、自动装配说明

- 启用开关：`plugin.distributed.enabled=true` 且存在 `StringRedisTemplate` Bean。
- `WORKER` 角色额外装配：`PluginInvocationServiceImpl`（gRPC 执行服务）、
  `GrpcServerBootstrap`（gRPC 服务端）、`ServiceRegistrationScheduler`（目录注册与心跳）。
- 所有角色装配：`RedisServiceDirectory`（目录）、`GrpcClientProvider`（连接池）、
  `RemoteServiceProxyFactory`、`DistributedServiceLocator`（静态门面）、
  `DistributedPluginServiceRegistry`（本地优先/远端兜底门面）。
- **透明替换（单一 Bean）**：`DistributedPluginServiceRegistry` 是全局**唯一**的
  `PluginServiceRegistry` Bean，通过 `@AutoConfigureBefore(SpringBootPluginStarter)` +
  `@ConditionalOnMissingBean` 抢占并替换主框架默认实现，无需 `@Primary`、无重复 Bean、
  无自引用循环。因此原有 `@Autowired PluginServiceRegistry` 或
  `ObjectProvider<PluginServiceRegistry>` 的代码，启用分布式模块后自动获得
  「本地优先、远端兜底」能力，调用方零改动。

## 八、设计要点与约定

1. **参数/返回值以 JSON 序列化**，携带类型信息，对端据此反序列化。执行节点按**插件类加载器**
   解析接口与参数/返回值类型（仅当接口在共享 classpath 时才回退应用类加载器），因此插件
   专属的 DTO 也能正确还原。复杂泛型/嵌套对象仍建议用共享 DTO / 简单 POJO。
2. **每次调用实时查目录**：支持执行节点上线/下线/迁移后自动切换，无需重启宿主。
3. **多副本轮询 + 故障转移 + 健康快速失败**：同一插件服务可注册到多个执行节点；调用侧用
   全局计数器轮询起始下标避免都压第一个节点，目标节点传输层不可达时自动切换到下一副本
   （`clients.evict()` 断开死连接），全部副本失败才抛错；业务异常不参与 failover，以原始
   类型还原抛出。**节点健康状态**：节点调用失败即进入冷却期（`GrpcClientProvider` 默认 2s，
   配合后续退避），存在健康节点时直接跳过冷却中的节点、不发起网络调用、不计 failover，
   避免在目录尚未剔除陈旧节点前每次都去撞同一台宕机节点；仅当本轮没有健康节点时才尝试
   死节点并快速失败。
4. **traceId 透传**：宿主 MDC 中若有 traceId，随 gRPC 请求头 `x-trace-id` 透传到执行节点，
   在执行线程恢复进 MDC，使跨节点日志处于同一条链路。
5. **心跳用 Redis TTL 实现**：服务记录过期即视为下线。实现上每个服务在 Redis 中是一个
   Hash key（TTL 由任一生效节点续期保活），**字段内记录 `registeredAt` 时间戳**，宿主查询时
   会依据该时间戳过滤掉「已超过心跳有效期未续期」的陈旧节点，避免把请求路由到崩溃的节点；
   同时自动清除这些陈旧字段，保持目录整洁。
6. **节点地址用局域网 IP**：执行节点注册的是可达的 IPv4 地址而非主机名，保证跨节点、
   容器、多网卡环境下宿主能够真正连通执行节点。
7. **按版本取服务**：`getServicesByVersion` 同样覆盖远端——用框架 `VersionRange` 过滤目录中
   远端注册的版本，命中的才建远程代理，与本地按版本语义一致。
8. **调用超时**：`plugin.distributed.call-timeout-millis`（默认 5000ms）。
9. **按节点协商的 TLS 加密（支持明文/TLS 混合）**：节点注册信息携带 `tlsEnabled` 标记，
   宿主按**每个节点**选择明文或 TLS 方式建连（channel 缓存键含 TLS 标记），因此支持
   「明文节点 + TLS 节点」混合部署，便于滚动灰度升级：`plugin.distributed.tls-enabled=true`
   时，执行节点用 `tls-cert-chain` / `tls-private-key`（PEM）启动 TLS 服务端，宿主用
   `tls-ca-cert` 校验对端证书。
10. **token 鉴权**：所有节点配置相同 `plugin.distributed.auth-token` 时，宿主每次调用会在
    gRPC 头（`authorization: Bearer <token>`）附带 token，执行节点校验不通过返回
    `UNAUTHENTICATED`。
11. **显式监听/注册 IP**：多网卡场景用 `plugin.distributed.host` 显式指定业务网段 IP
    （既是 gRPC 监听地址，也是写入 Redis 目录的对外可达地址），避免自动解析选错网卡。
12. **远端异常 cause 链精确还原**：执行节点抛出的业务异常，会把「异常类型 + 消息 + 根因
    （cause 的 errorType/message）」随 gRPC 一并回传。宿主侧若对应异常类对 classpath 可见
    （双方共享契约中包含异常类），则精确还原为该异常类型并级联重建 cause 链
    （`hasRootCauseInstanceOf` / 根因消息可断言，日志可完整追溯）；不可见的私有异常类则
    回退为 `RuntimeException`，在消息中保留原始 `errorType`。
13. **Redis 目录本地兜底缓存**：宿主 `RedisServiceDirectory` 每次查询成功后会刷新一份
    「last-known-good」内存快照；当 Redis 临时故障（连接断开/超时）时，`lookup` 降级返回
    最近一次成功快照而非空列表，保证已发现的服务在目录服务抖动期间仍可继续路由调用。
    快照保留时长由 `plugin.distributed.registry-cache-ttl-millis`（默认 30s）控制，超时后
    清空，避免把已下线的陈旧节点无限期路由。

## 九、限制与后续演进

- 泛化调用对「参数为接口/泛型/复杂嵌套对象」的精确还原能力有限，复杂场景建议改用
  共享 DTO 或独立微服务化（P3 阶段）。
- 消息大小默认 16MB，可通过 `plugin.distributed.max-inbound-message-size` 调整。
- 当前已支持：多副本轮询 / 故障转移、节点健康快速失败与冷却退避、traceId 链路透传、
  接口级版本路由（复用 `VersionRange`）、插件类加载器感知的类型还原、远端异常 cause 链
  精确还原、按节点协商的 TLS 加密（明文/TLS 混合）、token 鉴权、显式监听 IP、
  Redis 目录本地兜底缓存。
  后续可增强：gRPC 双向流式调用、基于持久化订阅的事件推送、
  面向宿主/网关的远端调用监控指标与熔断限流。

## 十、与既有集群能力的区别

| 能力 | 既有 ClusterNodeRegistry | 本分布式模块 |
|------|-------------------------|-------------|
| 作用 | 节点在线心跳 + 插件状态同步 | 服务接口级发现 + 远程执行 |
| 技术 | 共享文件 + 心跳 | Redis 目录 + gRPC |
| 是否本地执行插件 | 是 | 否（远端节点执行） |
| 解决「重复部署」 | 否 | 是 |
