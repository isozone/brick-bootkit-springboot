# 分布式插件：远端调用开发指南（手把手）

> 本文是《6.分布式插件(RemotePlugin).md》的**实操补充**，面向开发者一步一步搭建
> 「执行节点（WORKER）+ 宿主节点（HOST）」双节点环境，并完成一次真实的远端插件调用。
>
> 目标：10 分钟内跑通 `HOST 业务代码 → gRPC → WORKER 插件容器 → 返回结果` 全链路。

---

## 0. 先理解三个角色

| 角色 | 职责 | 是否加载插件 | 是否开 gRPC 服务端 |
|------|------|:---:|:---:|
| **WORKER 执行节点** | 加载真实插件、接收并执行远端调用 | ✅ | ✅（暴露端口） |
| **HOST 宿主节点** | 只做服务发现 + 远程代理，不装插件 | ❌ | ❌ |
| **单机混合节点** | 既承载部分插件、又消费其他节点插件 | ✅ | ✅ |

**核心心智模型**：插件部署在 WORKER，业务代码跑在 HOST。两者通过同一个 Redis 服务目录 + gRPC 相连。
调用方感觉不到任何差异，跟本地 `getService()` 一模一样。

---

## 1. 环境准备

- **JDK 17+**
- **Maven 3.6+**（首次构建会联网下载 protoc 与 grpc-java 插件）
- **Redis**：WORKER 与 HOST 必须指向**同一个** Redis（作为服务目录中枢）
- 本框架已 `mvn install` 过，`com.zqzqq:spring-boot3-brick-bootkit-distributed:4.0.10` 已入本地仓库

## 2. 步骤 0：定义共享契约接口

建议新建一个 **契约模块**（或放主应用 `src/main/java`），被 WORKER 和 HOST 同时依赖。

```java
// contract/UserService.java —— 全限定名唯一，两端都要能加载
public interface UserService {
    String getUserName(Long userId);
    UserInfo getUserInfo(Long userId);
    UserInfo getUserInfo(String name);   // 同名重载也能精确路由
}
```

```java
// contract/UserInfo.java —— 参数/返回值 DTO，建议共享、简单 POJO
public class UserInfo {
    private Long id;
    private String name;
    // getter/setter 必须齐全（Jackson 反序列化需要）
}
```

> 说明：执行节点侧已具备**插件类加载器感知**——即使接口只存在于插件 jar、不在共享
> classpath，也会从插件类加载器解析。但对外契约放共享模块语义最清晰，仍是推荐做法。

## 3. 步骤 1：搭建 WORKER 执行节点

### 3.1 pom 依赖

```xml
<dependency>
    <groupId>com.zqzqq</groupId>
    <artifactId>spring-boot3-brick-bootkit-distributed</artifactId>
    <version>4.0.10</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

### 3.2 配置 `application-worker.yml`

```yaml
server:
  port: 8081                    # Web 端口（与 gRPC 端口区分开）

spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379

plugin:
  enable: true
  pluginPath: [ ./plugins ]     # 插件放置目录
  distributed:
    enabled: true               # 关键开关
    role: WORKER                # 角色 = 执行节点
    port: 9090                  # 本节点 gRPC 端口，供 HOST 调用
    node-id: worker-1           # 强烈建议显式配置，保证身份稳定
    registry-prefix: brick-bootkit:distributed:services
    heartbeat-ttl-seconds: 30
    heartbeat-interval-seconds: 10
    call-timeout-millis: 5000
```

### 3.3 插件内实现并注册服务

插件类加载进 WORKER 时，框架会把声明 `@PluginService` 的实例自动注册到本地
`PluginServiceRegistry`；分布式调度器再把该能力同步到 Redis 目录。

```java
package com.example.worker.plugin;

import com.example.contract.UserInfo;
import com.example.contract.UserService;
import com.zqzqq.bootkits.core.communication.annotation.PluginService;

@PluginService(interfaceClass = UserService.class, version = "1.0.0", name = "user-service")
public class UserServiceImpl implements UserService {

    @Override
    public String getUserName(Long userId) {
        return "User-" + userId;
    }

    @Override
    public UserInfo getUserInfo(Long userId) {
        return new UserInfo(userId, "User-" + userId);
    }

    @Override
    public UserInfo getUserInfo(String name) {
        return new UserInfo(0L, name);
    }
}
```

### 3.4 启动 WORKER

```bash
mvn spring-boot:run -Dspring-boot.run.profiles=worker
```

启动成功后日志应出现：

```
分布式插件 WORKER 节点 gRPC 服务已启动，端口: 9090
```

## 4. 步骤 2：搭建 HOST 宿主节点

### 4.1 依赖（与 WORKER 相同，也可不含插件运行时）

```xml
<dependency>
    <groupId>com.zqzqq</groupId>
    <artifactId>spring-boot3-brick-bootkit-distributed</artifactId>
    <version>4.0.10</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

### 4.2 配置 `application-host.yml`

```yaml
server:
  port: 8080

spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379

plugin:
  distributed:
    enabled: true
    role: HOST
    call-timeout-millis: 5000
```

HOST 不启动 gRPC 服务端，只保留目录查询 + 远程代理能力。

### 4.3 方式一：`DistributedServiceLocator` 静态门面（推荐，无需注入）

```java
import com.zqzqq.bootkits.distributed.DistributedServiceLocator;

String name = DistributedServiceLocator.service("user-plugin", UserService.class)
        .getUserName(1L);
```

> `"user-plugin"` 必须与 WORKER 插件中实际注册的 `pluginId` 一致（`@PluginService` 所在插件的 ID）。

### 4.4 方式二：注入 `PluginServiceRegistry`（透明替换，调用方零改动）

```java
@Service
public class UserFacade {

    @Autowired
    private PluginServiceRegistry registry;   // 已是分布式门面，不用改名

    public UserInfo getById(Long id) {
        return registry.getService("user-plugin", UserService.class).getUserInfo(id);
    }
}
```

> 启用分布式模块后，全局唯一的 `PluginServiceRegistry` Bean 自动被替换为「本地优先、
> 远端兜底」的门面。这段代码与「单机插件模式」完全一致，无需任何改动。

### 4.5 放到 REST Controller 便于验证

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}/name")
    public String name(@PathVariable Long id) {
        return DistributedServiceLocator.service("user-plugin", UserService.class)
                .getUserName(id);
    }

    @GetMapping("/{id}")
    public UserInfo info(@PathVariable Long id) {
        return DistributedServiceLocator.service("user-plugin", UserService.class)
                .getUserInfo(id);
    }
}
```

### 4.6 启动 HOST

```bash
mvn spring-boot:run -Dspring-boot.run.profiles=host
```

## 5. 步骤 3：启动顺序与验证

### 5.1 启动顺序

1. 先启动 **Redis**；
2. 再启动 **WORKER**（把插件能力登记进目录 + 心跳续期）；
3. 最后启动 **HOST**（消费远端能力）。

WORKER 与 HOST 顺序其实不强依赖——HOST 每次调用会**实时查目录**，因此 WORKER 后启动
也能被即时发现；只要调用发生时 WORKER 已在线即可。

### 5.2 用 curl 验证

```bash
# 远端调用，结果来自 WORKER 插件容器
curl http://localhost:8080/api/users/1/name
# => User-1

curl http://localhost:8080/api/users/99
# => {"id":99,"name":"User-99"}
```

### 5.3 在 Redis 里确认服务已注册

```bash
redis-cli HKEYS "brick-bootkit:distributed:services:com.example.contract.UserService"
# => user-plugin@worker-1
```

```bash
redis-cli HGET "brick-bootkit:distributed:services:com.example.contract.UserService" "user-plugin@worker-1"
# => {"pluginId":"user-plugin","serviceInterface":"com.example.contract.UserService",
#     "version":"1.0.0","nodeId":"worker-1","host":"192.168.1.20","port":9090,...}
```

> 若心跳超时（默认 30s 未续期），该字段会被标记陈旧并在查询时自动清除。

### 5.4 确认 gRPC 调用真的发生在远端

在 WORKER 日志中应能看到调用与（如配置了）插件内打出的日志；
在 HOST 日志里可见远程代理命中节点的 `debug` 日志：

```
服务 user-plugin@com.example.contract.UserService 由远端节点 192.168.1.20:9090 提供，创建远程代理
```

## 6. 高级用法

### 6.1 单机同时承载 + 消费

把 HOST 也配成 `role: WORKER` 即可。本地能解析的服务走本地，本地没有的自动路由远端。

### 6.2 多副本 + 故障转移

同一插件部署到多个 WORKER（如 `worker-1`、`worker-2`，node-id 不同）。调用侧自动在
多副本间**轮询**；某个 WORKER 宕机时**自动切换到健康副本**，业务无感。

```
node-id: worker-1   # WORKER-A
node-id: worker-2   # WORKER-B（同样加载 user-plugin）
```

日志中可见故障转移：

```
节点 192.168.1.20:9090 不可用，切换到下一副本继续调用: com.example.contract.UserService
```

### 6.3 按版本取服务

```java
List<UserService> v2 = registry.getServicesByVersion(UserService.class, "[2.0,3.0)");
```

会同时匹配本地与远端目录中版本落在 `[2.0,3.0)` 的服务。

### 6.4 traceId 链路透传

在 HOST 侧线程放入 `traceId` 到 SLF4J MDC，远端插件内日志即处于同一条链路：

```java
org.slf4j.MDC.put("traceId", "req-abc-123");
String name = ...getUserName(1L);   // 远端日志带同一 traceId
org.slf4j.MDC.remove("traceId");
```

### 6.5 安全配置（TLS + token 鉴权 + 多网卡 IP）

生产跨网段/公网传输务必开启 TLS 与鉴权。**所有节点必须一致启用**。

**WORKER 执行节点**（需证书与私钥）：

```yaml
plugin:
  distributed:
    role: WORKER
    host: 10.0.0.21              # 多网卡时显式指定业务网段 IP（监听 + 注册地址）
    tls-enabled: true
    tls-cert-chain: /etc/brick/certs/server.crt   # PEM 证书链（含叶子 + 中间证书）
    tls-private-key: /etc/brick/certs/server.key  # PEM 私钥（PKCS#8）
    auth-token: change-me-shared-secret           # 两端必须一致
```

**HOST 宿主节点**：

```yaml
plugin:
  distributed:
    role: HOST
    tls-enabled: true
    tls-ca-cert: /etc/brick/certs/server.crt      # 校验执行节点证书（信任该 CA）
    auth-token: change-me-shared-secret           # 与执行节点一致
```

> ⚠️ 说明：
> - TLS 与 token 的启用状态**所有节点必须一致**（要么全部明文，要么全部启用）。
> - `tls-ca-cert` 点为「信任执行节点证书的 CA”。若执行节点用自签名证书，直接把该自签证书
>   填给 `tls-ca-cert` 即可。
> - token 建议搭配 TLS，避免明文传输。

> 🔑 **安全自检**：配置错误 token 会收到 `UNAUTHENTICATED`；未正确信任 CA 会握手失败
> （`UNAVAILABLE`）。`GrpcServerBootstrap` 启动日志中出现 `已启用 TLS` 即代表服务端加密生效。

> 🚀 **一键生成证书**：运行
> `spring-boot3-brick-bootkit-distributed/gen-cert.sh`（Linux/macOS/Git Bash）或
> `gen-cert.bat`（Windows），自动产出 `server.key` / `server.crt` / `ca.crt`
> 三件套并打印两端 yml 建议。例如：
> `./spring-boot3-brick-bootkit-distributed/gen-cert.sh --ip 127.0.0.1 --ip 10.0.0.21`

## 7. 常见问题排查

| 现象 | 原因与排查 |
|------|-----------|
| `远端服务不可用，未在任何执行节点注册` | 该插件未在 WORKER 加载/注册，或 Redis 目录里没有该 pluginId@iface 记录。检查 WORKER 是否启动、`HKEYS` 是否可见。 |
| `节点不可达 / UNAVAILABLE` | gRPC 连不上 WORKER。核对 WORKER 的 `plugin.distributed.port` 与 HOST 实际访问端口；检查防火墙。 |
| `UNAUTHENTICATED` | 鉴权失败。核对两端 `auth-token` 是否一致、是否有一端启用了 token 而另一端未启用。 |
| 开启了 TLS 但连接不稳定/握手失败 | 两端 `tls-enabled` 不一致，或 HOST 未正确配置 `tls-ca-cert`。所有节点必须统一开启，且 HOST 信任的证书包含 WORKER 的证书。 |
| `服务接口未加载` | 接口类名找不到。确认契约接口在 WORKER 侧 classpath 可见（或放入插件 jar）。 |
| Redis 连不上 | WORKER/HOST 的 `spring.data.redis.*` 是否指向同一实例、密码是否正确。 |
| 调用到已下线节点 | 陈旧注册未及时清除。属正常容错——调用会自动 failover 到健康副本，请确认有 ≥2 副本或该节点已恢复。 |
| 多节点下结果不稳定 | 未配 `node-id`，节点身份不稳定。**强建议**显式配 `node-id`。 |

## 8. 最小自检清单（单机即可验证闭环）

1. 本机起 Redis；
2. 起一个 `role=WORKER` 的应用，加载含 `UserServiceImpl` 的插件；
3. 起一个 `role=HOST` 的应用，配好 Redis；
4. `curl http://<host>:8080/api/users/1/name` 返回 `User-1`;
5. `redis-cli HKEYS ...` 能看到 `user-plugin@node-id`；
6. 停掉 WORKER 后再次调用，得到清晰的「不可用」提示（而非崩溃/挂死）。

全部通过，即说明「插件本地部署 → Redis 目录登记 → HOST 透明远端调用」已真正闭环。
