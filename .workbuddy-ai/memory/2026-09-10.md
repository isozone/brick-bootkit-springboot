## 痛点方向：旧项目如何快速接入

拆解为四阶段，并核实现状（结论用于后续方案设计）：

- **可行性评估**：空白。所有现有工具（doctor）都是运行时工具，必须先接入才能用，存在鸡生蛋问题。
- **依赖引入**：文档齐全，但存在版本漂移（doc/2、doc/7 仍写 4.0.6，实际 4.0.11）。
- **启动适配**：`mainPackage` 推断实现在 `ExtendPointConfiguration#autoDetectMainPackageIfPossible`，
  依赖 `AutoConfigurationPackages.get()` 取第一个包。旧项目多 `scanBasePackages` / 非标准启动类时会不准，
  推断过宽会导致插件类被主加载器抢走（表现为难排查的 ClassCastException）。
- **业务切片**：完全无工具。core 已依赖 ASM 9.6，具备做静态分析的基础。

## 已落地：A + B（用户拍板先做这两个）

### A. preflight 体检器

- 位置 `tools/preflight/`：`Preflight.java`（零依赖单文件）+ `preflight.sh`。
- 运行方式：JDK 单文件源码模式，`./tools/preflight/preflight.sh <项目路径> [--json]`。
  不编译、不改目标项目、不下载依赖。退出码 0=无阻断 / 1=有阻断 / 2=参数或路径错误（可直接进 CI）。
- 检查项前缀 `PFxxx`：SB 版本、JDK 版本、packaging（war/pom 聚合）、Gradle、启动类唯一性、
  多 `scanBasePackages`、webflux、security、fastjson1、Java Agent（skywalking/arthas/jacoco）、
  dubbo/shardingsphere、多模块。输出建议 mainPackage + 推荐接入级别（NONE/L0/L1）。
- 踩过的坑（已修）：
  1. pom 里 `${spring-boot.version}` 占位符需递归解析，否则版本判断失效。
  2. 启动类识别必须用行首注解正则（`(?m)^\s*@(SpringBootApplication|EnableAutoConfiguration)\b`），
     `content.contains(...)` 会把注释/字符串里的同名文本误判成启动类。
  3. 多模块只扫 `<modules>` 声明链，否则 templates/、未参与构建的 demo 模块会污染结果。
  4. packaging 只取根 pom，子模块不能覆盖（否则父工程 pom 类型被子模块 jar 冲掉/反之）。

### B. 渐进式接入分级

- 新增 `AdoptionLevel` 枚举（SHADOW / OBSERVE / ACTIVE）在 `com.zqzqq.bootkits.integration`。
- `IntegrationConfiguration` 新增 `autoLoadPlugins()` / `autoStartPlugins()`（默认 true = 历史行为）
  与推导方法 `adoptionLevel()`；`AutoIntegrationConfiguration` 增加对应字段与 override。
- 拦截点在 `DefaultPluginOperator#initPlugins`：
  `autoLoadPlugins=false` 在 `loadPlugins()` 前返回（影子模式，Bean 全装配但不读插件目录）；
  `autoStartPlugins=false` 在 `loadPlugins()` 后、启动循环前返回（观察模式）。
  两者都置 `IS_INIT=true` 并打中文日志。
- doctor 新增 `ADOPTION_LEVEL_SHADOW/OBSERVE` 警告项（docAnchor=`adoption`）。
- **坑**：Mockito mock 接口时 default 方法返回 null，`adoptionLevel()` 会 NPE，
  故 doctor 中必须做 null 判断；既有用 mock 的 doctor 测试依赖这一点保持绿色。
- 配置元数据已补 `plugin.autoLoadPlugins` / `plugin.autoStartPlugins` 两项。
